## What to build

The explicit keep/discard layer on top of session persistence — web parity
with `SaveDialog` and `SavedWorkBrowser`, in SwiftUI-native presentation.

- **Saved flag semantics**: documents start unsaved; a document becomes
  saved when the user explicitly chooses to keep it. When the session is
  saved, unsaved documents that are no longer open in any tab are removed
  from the store (web parity — closed-and-discarded work does not
  accumulate).
- **Close-tab save dialog**: closing a tab with an *unsaved* document
  replaces issue 264's interim discard alert with the web's three-way
  choice — save (with a name field prefilled from the tab name), delete,
  or cancel. Saving marks the document saved under the chosen name and
  closes the tab; deleting closes the tab and drops the document; cancel
  leaves everything untouched. Closing a tab whose document is already
  saved closes immediately, no prompt.
- **Saved work browser**: an entry point in the top area (web parity: the
  TopBar browse affordance) opens a browser listing saved documents —
  thumbnail (export composite), name, dimensions, last-updated — excluding
  documents already open in a tab. Selecting one opens it in a new tab with
  a default viewport (web parity: reopening resets the view); each entry
  can also be deleted from the store. An empty state shows when nothing is
  saved.

i18n: new user-facing strings go through the String Catalog.

## Acceptance criteria

- Closing an unsaved tab offers save / delete / cancel; each branch behaves
  as described above. Closing a saved tab never prompts.
- A saved document survives being closed and relaunching, and appears in
  the browser with its thumbnail, name, dimensions, and updated time.
- Opening from the browser adds an active tab with the document's content
  and a reset viewport; that document disappears from the browser list
  while open.
- Deleting from the browser removes the document permanently; an unsaved
  document that was closed via delete (or discarded) is gone from the
  store after the next session save.
- Dialog/browser flow logic is unit-tested; the new surfaces appear in
  docked-view snapshots; a simulator pass verifies the end-to-end
  save → close → browse → reopen loop.

### Key Decisions

- Flow logic lives in a dedicated `SaveFlow` model (not `AppSession`, not view `@State`) so the whole dialog/browser flow is unit-testable against an in-memory store — the Apple analog of the web's `modal-state` + page handlers.
- Browser thumbnails pre-upscale the composite via a nearest-neighbor `CGContext` pass: `Image.interpolation(.none)` alone does not survive every render path (offscreen snapshots interpolate regardless).
- Sheet dismissal (swipe/Escape) resolves as cancel/close through presentation bindings, so no state is stranded.
- The destructive button tint stays view-local in both surfaces, mirroring the web's component-scoped `--_destructive`.
