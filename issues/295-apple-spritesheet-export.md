## What to build

Add the spritesheet format to the 294 export surface:

- **Spritesheet PNG**: every frame's composite as one horizontal strip
  (the 293 encoder), exported through the platform file-export flow with
  a filename that distinguishes it from the single-frame PNG (web naming
  convention as reference).
- Works for a single-frame document (a one-tile sheet) — no artificial
  frame-count gate, matching the web.
- The `SheetTooLarge` error (absurd frame counts) surfaces through the
  export-error presentation with the core's actionable message.

## Acceptance criteria

- Exporting a multi-frame document yields a PNG of canvas width × frame
  count by canvas height whose tiles match each frame's composite in
  axis order.
- A single-frame document exports a one-tile sheet identical to its
  frame composite.
- The active frame and document state are untouched by an export.
- New labels in the String Catalog (en/ko/ja).

### Key Decisions

- **`stemSuffix` on `ExportFormat`**: the web registry lets a format override its
  default filename stem (`spritesheetDefaultStem` → `-sheet`); the Apple registry
  mirrors that as a declared property so `TabState`'s filename builder stays
  format-agnostic and GIF (296) slots in without touching it.
- **Label localization split**: PNG/SVG stay untranslated acronyms (294 decision);
  "Spritesheet" is a word and localizes via the String Catalog, matching the web's
  localized `format_spritesheet`. The `String(localized:)` comment matches the
  catalog comment so build-time extraction stays stable.
- **`SheetTooLarge` needs no new code**: the 294 error alert already presents
  `AppleError`'s `LocalizedError` description, which carries the core's actionable
  message; the core notes the branch is unreachable through the public API (canvas
  dimensions are capped), so no shell-side test constructs it.
